# 保守と公開

公開版だけを編集し、非公開環境のディレクトリや Git 履歴をコピーしません。管理対象は README、導入手順、公開ドキュメント、テンプレート、payload、installer、manifest、tests、CI のみです。

1. 変更の完成条件・証拠・禁止条件・判断者・戻し方を決めます。
2. payload とコードを変更し、版と manifest を揃えます。manifest のチェックサムは、レビュー済みの payload から保守者が更新します。導入時の不一致を無理に通すために再生成しません。
3. まず空の隔離フォルダーで plan → apply → verify → rollback を通します。その後、既存指示の保持、重複実行、手編集の競合、途中失敗からの復旧、チェックサム不一致を試験します。
4. `python3 -m unittest discover -s tests -v` と `python3 scripts/check_release.py` を実行します。コマンドは保守を担当するエージェントが扱います。
5. 制作者と別の担当（別のモデルまたは別の文脈）で、コードと公開内容を確認します。個人情報・顧客情報・社内の接続先・秘密・権利不明の素材があれば公開しません。
6. `docs/VERIFICATION.md` に実際の環境、版、結果、未確認を記録します。テストログやマシンの絶対パスは公開しません。
7. 公開対象ファイルだけをコミットします。公開後、公開ページで表示を読み戻し、別のフォルダーで導入を通して確認します。

実運用から得た学びは、固有の事情（特定の顧客・端末・人物）を落として一般化してから、payload とドキュメントへ反映します。1件だけの事情を全体のルールにしません。
