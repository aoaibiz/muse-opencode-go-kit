# 受付と通知の仕組み

窓口と実行側の間で、仕事と返事を取りこぼさないための具体的な設計です。

## 受付（窓口 → 実行側）

- 実行側の PC に、依頼を受ける入口（受付）を1つ用意します。窓口は常にこの入口だけを使います。実行側のエージェントを直接もう1つ起動する経路は作りません（本線の作業と衝突します）。
- 受付は依頼文を受け取り、受付番号を返します。依頼は実行側の記録（作業ログ）へ自動で写されます。
- 返事は受付番号で引きます。長い作業は「送って待つ」形にせず、受付番号を返して切り上げ、後から結果を取りに行く形（非同期）にします。
- 依頼文は文章で書きます。コマンドや実行手順を埋め込むと、受け手側の安全確認で止まることがあります。

依頼文の型は `templates/request.example.md` にあります。

受付の入出力の例（値は一般化したものです）：

```text
窓口 → 受付：依頼文（達成すること／対象／完成条件／使ってよいモデル）
受付 → 窓口：受け付けました req-20260101-0001
窓口 → 受付：結果をください req-20260101-0001
受付 → 窓口：完了。本文は＜結果の要約＞、検証結果は＜…＞、残る問題は＜…＞
```

## 通知（実行側 → 窓口）

- 実行側は、返事や追記ができた時点で「合図ファイル」へ1行追加します。1行は「時刻＋種別＋受付番号」の形です。行の例：

```text
2026-01-01T09:12:33+09:00 reply req-20260101-0001
2026-01-01T09:40:05+09:00 append req-20260101-0001
```
- 窓口側の見張りは短い間隔（例：60秒）で合図ファイルを読み、新しい行があれば該当の返事を回収して利用者へ報告します。
- **重複の判定は行単位**です。既読の管理は「どの行まで読んだか」で持ちます。受付番号単位で管理すると、同じ番号への追記（あとから足された返事）が既読扱いになり、見逃します（実際に起きた事故）。
- 合図ファイルが取れない時の保険として、受付の回答一覧を定期的に照合する経路も用意します。ただし本線は合図です。
- 朝の横断確認のような定期のまとめは、この仕組みの保険として置きます。本線の代わりにはしません。

## 実行側のセッション保持

- 実行側のエージェントは、ターミナルのセッション保持（例：tmux の常駐セッション＋自動再起動のループ）で生かし続けます。接続のたびに起動し直す形にすると、長い作業と文脈が切れます。
- 利用者が端末で作業を見られるよう、常時表示の入口（セッションへ接続するスクリプト）を用意します。裏側で起動し直した時は、表示側の接続も付け直します。なお、リモート接続のシェルから画面つきのプロセスを起動しても、利用者のデスクトップには表示されません。対話セッションで起動する仕組み（タスクスケジューラの対話実行など）を使います。

## 鍵が要る道具の回し方（GUI セッションの実行役）

一部の道具は、利用者のログインセッション（キーチェーンなど）が無いと動かせません。そういう道具は次の形で回します。

1. 利用者の GUI セッションで常駐する小さな実行役（例：macOS の LaunchAgent）を置きます。
2. 窓口は、実行したい処理をファイル（ジョブ）としてキュー用のフォルダーへ置きます。
3. 実行役がキューを順に実行し、結果フォルダーへ出力を書きます。出力ファイルの末尾に終了の印（例：終了コードの行）が付いたら完了です。
4. 窓口は結果ファイルを回収します。

ヘッドレスな経路（SSH の通常セッションなど）では鍵が開かず動かせない道具があるため、この迂回が要ります。実行役は読み取り中心にし、送信などの操作は利用者が指定した対象だけに限ります。

## 完了の扱い

- 窓口は「受付に送った」「実行が始まった」を完了としません。結果を回収し、本番で確かめて初めて完了です。
- 相手からの返事・追記は、受け取り確認だけの内容でも利用者へ1行は届けます。完全に同じ内容の再送だけを落とします。
