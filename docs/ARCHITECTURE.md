# 構成の詳細

## 役割分担

| 担当 | 仕事 | 課金 |
|---|---|---|
| Muse（窓口） | 壁打ち、目的と条件の整理、実行依頼、結果の回収と説明 | 無料枠（週の上限あり） |
| Muse のクラウド VM | SSH 経路で PC へ仕事を渡し、成果物を受け取る | 窓口に含む |
| PC 上のハーネス | ファイルの読み書き、コマンド実行、検証 | なし（自分の PC） |
| OpenCode Go のモデル | コード生成、原因分析、修正案などの推論 | Go の共通枠 |
| PC 側の結果記録 | 変更点、検証結果、残る問題、利用量 | なし |

API のモデルだけでは PC のファイル編集やテストは実行されません。その処理を実際に行うエージェントとして、ハーネスを PC に置きます。

## 仕事の流れ

1. 利用者が窓口へ依頼する（スマホでも PC でもよい）。
2. 窓口が依頼を短くまとめ（達成すること・作業場所・完成条件・使ってよいモデル）、受付を通して PC 側へ渡します。受付番号が返ります。
3. PC 側のハーネスが、案件のルールと必要スキルを読んでから実行する。長時間の作業は接続が切れても継続する。
4. 完了したら PC 側に結果（変更点・検証結果・未解決点・利用量）を記録し、合図を出す。
5. 窓口が合図を検知して結果を回収し、本番で確かめてから利用者へ報告する。

同じ依頼が二重に届いた場合は受付番号で1件として扱い、同じファイルへの同時編集は直列化または作業場所の分離で防ぎます。受付と通知の具体的な設計は [受付と通知の仕組み](INTAKE.md) にあります。

## モデル選択

- 既定は安価なモデル。難しい設計、検証の失敗、最終判断で上位へ切り替えます。
- 切り替えの回数と再試行には上限を設けます。多数のモデルへ毎回相談させる使い方はしません。
- レビュー担当は、実装担当と別のモデルにします。エイリアスが実際にどのモデルへ解決されるかを確認し、記録には実モデル名を書きます。
- 逃げ道（フォールバック）を用意する場合は、「何が起きたら・どのモデルへ」切り替わるかを先に決め、切り替えが実際に起きた時に分かるよう記録します。通常時は既定の経路のままにします。

## 利用量の見方

- Go は共通枠で、5時間・週・月の上限があります。PC の画面でもスマホのウィジェットでも、同じ実測値が古くならないよう、表示は常に最新の数字が自動で読める状態にします。
- 窓口（Muse）の無料枠にも週の上限があります。窓口の消費は、依頼を短くし、完了報告を短くすることで抑えます。生ログやコード全文を窓口へ常時返さないことも効きます。
- 増枠（Go Plus など）の判断は、実測の消費が枠へ当たる頻度を見てから行います。「当たりそう」では判断しません。
